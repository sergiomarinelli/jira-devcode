Manual triggers plus web requests are a perfect recipe for duplicate executions.

In this post, you’ll learn a production-friendly pattern to **prevent duplicates**, **control concurrency**, and **persist state** using a lightweight state store.

**You’ll get:**
- ✅ <Outcome 1>
- ✅ <Outcome 2>
- ✅ <Outcome 3>

---

## The pain
Describe the real-world problem in 4–8 lines.

- People click the rule twice.
- Two admins run it “just to be sure”.
- Two automations race.
- You get duplicated comments, repeated API calls, inconsistent data.

**Typical symptoms**
- Duplicate actions (comments/transitions/requests)
- Backlog noise and rework
- External systems receiving duplicated “create” calls
- Hard-to-debug “it ran twice” behavior

---

## The goal
What success looks like:

- Only one execution runs per issue at a time (lock)
- A “create” operation will not run twice for the same issue (idempotency)
- Async jobs can be started once and finished later safely
- Retries happen only when needed (and are capped)

---

## When to use this
Use this when:
- You have **manual triggers** or **web requests** that can be clicked/run more than once
- You call external APIs that are not safe to repeat
- You need basic orchestration without apps or databases

Avoid this when:
- You truly need cross-issue locking or global state (entity properties are per-entity)
- A workflow validator/condition can solve the problem more cleanly

---

## How it works (high level)
**Core concept:** store execution state on the issue using **Entity Properties** (JSON key/value).

Automation can:
- Set properties via **Set entity property**
- Read them via smart values like `{{issue.properties.myKey}}`
- Use them in advanced conditions (guardrails)

---

## What are Entity Properties
Entity properties are JSON blobs stored against Jira entities like issues, projects, and users.

In Jira Automation rules, you can:
- **Set** them via “Set entity property”
- **Read** them via smart values:
  - `{{issue.properties.<key>}}`
  - `{{issue.properties.<key>.status}}`
  - `{{issue.properties.<key>.attempts}}`

Think of them as a small state record attached to the issue.

---

## Naming convention (recommended)
Keep keys predictable and searchable:

- `automation.lock.<ruleKey>`
- `automation.idempotency.<operation>`
- `automation.job.<integrationName>`
- `automation.retry.<operation>`

Examples:
- `automation.lock.manualSync`
- `automation.idempotency.createExternal`
- `automation.job.externalSync`
- `automation.retry.externalSync`

## Pattern 1: Per-issue lock (manual trigger anti-duplication)
**Goal:** if the rule is clicked twice, the second execution exits immediately.

### Property key
```text
automation.lock.<ruleKey>
```

Example:
```text
automation.lock.manualSync
```

### Rule flow
1) **Trigger:** Manual trigger  
2) **Condition (Advanced compare):** lock is empty  
   - First value: `{{issue.properties.automation.lock.manualSync}}`  
   - Condition: **is empty**  
3) **Action:** Set entity property (create lock)  
   - Entity: Issue  
   - Property key: `automation.lock.manualSync`  
   - Value:
```json
{
  "status": "running",
  "runId": "{{rule.id}}-{{executionId}}",
  "startedAt": "{{now}}"
}
```
4) **Do your work**
   - Edit issue
   - Transition
   - Web requests  
5) **Release lock** (mark done)  
   - Set the same property key to:
```json
{
  "status": "done",
  "runId": "{{rule.id}}-{{executionId}}",
  "finishedAt": "{{now}}"
}
```

### Why it works
The first execution sets a flag; parallel executions see the flag and stop.

## Pattern 2: Idempotency key (do not repeat side effects)
**Goal:** prevent repeating the same operation later, even if a lock is cleared.

Use this for “create” style operations:
- creating a resource in an external system
- provisioning an account
- calling a `POST /create` endpoint

### Property key
```text
automation.idempotency.<operation>
```

Example:
```text
automation.idempotency.createExternal
```

### Flow
1) **If** `{{issue.properties.automation.idempotency.createExternal}}` is **not empty** → **Stop rule**  
2) Else → perform the operation  
3) Set the property to remember completion:
```json
{
  "done": true,
  "doneAt": "{{now}}",
  "by": "{{initiator.accountId}}",
  "issueKey": "{{issue.key}}"
}
```

### Tip: align with external API idempotency (if supported)
If your API supports an idempotency header, send a stable key like:
```text
{{issue.key}}:createExternal
```

## Pattern 3: Wait-for-API without duplicating calls (async orchestration)
**Goal:** start a job once and finish later safely.

Many APIs work like:
- `POST /jobs` → returns `jobId` immediately
- `GET /jobs/{jobId}` → later returns `DONE/FAILED`

A safe approach is two-step orchestration: **Starter rule** + **Poller rule**.

### Step A: Starter rule (create job once)
- Trigger: manual trigger or issue event
- Guards: lock + idempotency (Patterns 1 and 2)
- Action: Send web request to create the job

Store the job id:

Property key:
```text
automation.job.externalSync
```

Stored JSON:
```json
{
  "status": "started",
  "jobId": "{{webResponse.body.jobId}}",
  "startedAt": "{{now}}",
  "attempts": 1
}
```

### Step B: Poller rule (continue later)
Trigger options:
- Scheduled rule every X minutes + JQL filter
- Or a rule triggered by a field change (if you control state via a custom field)

JQL idea (only issues with a running job):
```text
issue.property[automation.job.externalSync].status = "started"
```

Then:
- Send web request:
```text
GET /jobs/{{issue.properties.automation.job.externalSync.jobId}}
```
- If status == DONE → update issue and mark property as done
- If status == FAILED → store error and decide whether to retry
- If still running → do nothing and let the schedule run again

Mark completed:
```json
{
  "status": "done",
  "jobId": "{{issue.properties.automation.job.externalSync.jobId}}",
  "finishedAt": "{{now}}",
  "result": "{{webResponse.body.result}}"
}
```

Mark failed:
```json
{
  "status": "failed",
  "jobId": "{{issue.properties.automation.job.externalSync.jobId}}",
  "failedAt": "{{now}}",
  "lastError": "{{webResponse.status}} - {{webResponse.body}}"
}
```

## Pattern 4: Stale lock takeover (avoid being stuck forever)
Runs can crash or time out, leaving a lock in `running` forever.

Timeout policy example:
- If lock is older than 10–30 minutes, consider it stale and allow takeover.

Lock JSON should store a timestamp (Pattern 1 already does):
```json
{
  "status": "running",
  "runId": "rule-123-exec-456",
  "startedAt": "2026-01-14T03:00:00Z"
}
```

Start-of-rule decision:
- If lock is empty → proceed
- Else if lock is running and stale → overwrite lock and proceed
- Else → stop

---

## Pattern 5: Safe retries with an attempts counter
Retries are dangerous when operations have side effects. Make retries explicit:

Property key:
```text
automation.retry.externalSync
```

Stored JSON:
```json
{
  "status": "failed",
  "attempts": 2,
  "lastAttemptAt": "{{now}}",
  "lastStatus": 502
}
```

Retry policy example:
- If attempts >= 3 → stop and notify
- If lastStatus is 429/502/503/504 → retry
- Otherwise → stop and require manual intervention

## Troubleshooting
**Problem:** rule runs twice  
**Cause:** no lock/idempotency guard  
**Fix:** implement Pattern 1 (lock) + Pattern 2 (idempotency)

**Problem:** stuck in running  
**Cause:** execution crashed before releasing lock  
**Fix:** implement Pattern 4 (stale takeover)

**Problem:** external API spam  
**Cause:** retries without cap  
**Fix:** implement Pattern 5 (attempts + retry policy)

---

## Checklist before you ship
- [ ] Does the rule exit safely if triggered twice?
- [ ] Does it avoid repeating create operations?
- [ ] Are failures stored somewhere (property, comment, field)?
- [ ] Is there a stale timeout to avoid stuck locks?
- [ ] Do retries have a cap?

If you implement just Pattern 1 (lock) and Pattern 2 (idempotency), you already eliminate most duplicate execution pain.
